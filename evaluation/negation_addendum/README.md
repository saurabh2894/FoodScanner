# Negation addendum: real labels with genuine negation lines (pre-registered, build dd13c04)

Why: batch 3's negation control (Q13) held no negation (the selection pattern 'contains no' matched 'Contains Non-Caloric'). Negation scoping can flip a group, so it needs real labels.
Selection (stated before reading any result): Open Food Facts India, code prefix 890, English ingredients text of at least 10 characters, not any code seen in batches P, F, N, M, 1, 2, 3 or development; text matched by a word-bounded pattern
(contains no / no added (not sugar) / does not contain / free from / no artificial / no preservative(s) / no colour(s) / no flavour(s) / gluten free) across about 40 India categories (top scanned pages), then 6 labels chosen by hand to cover: negation of colour/flavour/preservative with NO code deciding the group (R1, R2),
a mixed positive-plus-negative line (R3 same sentence; R6 two positive Contains sentences plus one negation), a negation after a code-bearing list (R4), and an allergen-free / may-contain statement (R5). Hand choice, no random draw, no per-label replacement; the other candidates found (sugar-claim negations such as 'No added sugar', 'Contains no fruit' variants) were not used.
Pasted input = untouched record text (inputs/). Photos run in the browser harness except R5 (its photo shows the nutrition table, no ingredient list; R5 is paste only). Expected groups and criteria are in references.json, hashed (SHA-256) in REFERENCES.sha256 BEFORE any run; the whole addendum lands in one commit (owner direction), so unlike batches 1-3 the pre-registration is the hash recorded here, not a separate earlier commit.
No code change between this and dd13c04 in src/, web_preview/, scripts/ other than the parity corpus. One frozen-build sample, not an accuracy claim; references are LLM-prepared from photos and need the owner's spot-check.
